## 一、这是一份什么文档

不是分析报告，而是**上线审批台账**：北美 push 场景下一批风控策略在正式生效前，逐条走
「配置前评估 → 发布前评估 → leader 审批」流程的记录。文档由两部分组成：

| 章节 | 作用 |
|---|---|
| 一、配置前评估表 | 字段定义模板。用于判断策略是否可以进入配置阶段，重点防止**规则本身设计错误、对象理解错误、误伤风险未识别** |
| 二、发布前评估表 | 逐策略的评估记录。用于判断策略是否可以正式上线，重点防止**样本不足、观察不足、误伤未识别、未经审批扩范围** |

## 二、审批范围

本次审批共覆盖 **28 条策略**，分四组：

| 组别 | 条数 | 说明 |
|---|---|---|
| REJECT 策略 | 11 | 命中即拦截 |
| REVIEW 策略 | 10 | 命中转人工 / 二次校验，多数处于观察态 |
| 待上线（兜底策略） | 4 | 仅列出清单，尚未配置 |
| 待上线（确认人机识别） | 3 | 依赖人机识别能力确认后再配置 |

判定维度可归为四类：**区号与 IP 归属**、**IP / IP 段的手机号聚合**、**手机号行为频次**、
**人机识别分与客户端标识**。各策略与维度的具体对应关系、统计窗口与门槛值均不公开。

## 三、评估表要求填写的字段

这是本文档中最具参考价值、也最适合公开的部分 —— 一条风控策略上线前，评估表强制要求回答的问题：

**规则设计层面**
- 策略目标、上线原因、规则逻辑、阈值说明、处置动作、生效范围
- 字段语义是否确认、字段取值来源是否确认
- 是否存在近义字段混淆风险
- 接口类型判断（C 端 / 其他）
- 是否存在正常聚合流量风险（IP、设备、账号等）
- 是否已了解接口业务背景、是否识别潜在误伤人群
- 是否需重点关注系统稳定性风险

**观察充分性层面**
- 预上线开始时间、实际观察时长
- 报错大盘是否检查、检查结论
- 是否覆盖核心活跃时段 / 主要用户场景 / 活动高峰与典型周期

**样本与准确性层面**
- 整体调用量、整体用户量、命中样本量、风险样本量、暂无法判断样本量
- 准确率、误伤比例
- 是否达到最低整体调用量 / 最低整体用户量 / 命中样本参考门槛

**黑产判定依据层面**
- 代下行为是否明显、IP / 设备是否聚集、手机号是否命中猫池或高风险标签
- API 链路是否异常、设备指纹是否高风险、礼品卡转赠是否异常
- 黑产评估依据说明（多行文本，必填）
- 近 7 日同期平均调用量 / 用户量

**审批与兜底层面**
- 是否符合上线标准、是否申请例外审批、例外类型、例外原因、补充控制措施
- 发布前评估结论、leader 审批结论、leader 审批意见
- 上线后监控责任人、当前状态

## 四、审批结论分布

审批不是走过场 —— 相当一部分策略被**退回**而非通过。结论可归为四类：

| 结论类型 | 说明 |
|---|---|
| 审批通过 | 规则、样本与依据均被接受，可上线 |
| 退回 —— 阈值不合适 | 规则方向认可，但审批人认为门槛设置过松或过紧，要求改值后再报 |
| 退回 —— 黑产依据不足 | 命中的确实异常，但现有证据不足以证明是黑产，要求补充证据后再报 |
| 待审批 / 未填结论 | 观察态策略，或「当前状态」栏未填写 |

**被退回时，审批人给出的典型意见**（已去除其中的具体数值与规则文本）：

- 「需调整，感觉有风险」—— 要求重设门槛后再报
- 「评估依据不足以说明是黑产，需进一步确认：IP 是美国吗，手机号是哪的」
- 「评估依据不足以说明是黑产，是否存在正常人频繁发送短信引起」
- 门槛取值被判定为不合适 —— 出现多次，要求重设后再报
- 部分策略的「当前状态」栏直接记录了规则改写结论，而非审批状态

## 五、评审中反复出现的质量问题

这些是台账本身暴露出来的系统性问题，对任何做风控策略评审的团队都有参考价值：

1. **准确率在零命中样本上仍记为 100%。** 多条策略的命中样本量为 0，准确率栏却填 100%、误伤比例填 0。
   分母为零时该指标没有意义，却仍被用作「符合上线标准」的依据。

2. **「是否达到命中样本参考门槛」大面积空白。** 该项为必填，但在多数策略中未填写 ——
   恰恰是这一项本该拦住上一条问题。

3. **黑产评估依据填「-」。** 该字段为必填，部分策略以「-」占位即通过评估，
   与 SOP「不得单一特征定性」的要求相冲突。审批人对其中几条的退回意见正源于此。

4. **必填的审批字段整体空白。** 「发布前评估结论」「leader 审批结论」「上线后监控责任人」
   在多数策略中为空，但「当前状态」已标记为审批通过。审批链路的留痕不完整。

5. **风险画像六项几乎全部未填。** 代下行为、IP / 设备聚集、猫池标签、API 链路、
   设备指纹、礼品卡转赠 —— 这六项是判定黑产的结构化依据，实际填写率极低，
   导致黑产判定退化为自由文本描述。

6. **「当前状态」栏被当作自由文本批注栏使用。** 实际取值混杂了审批状态、
   规则改写记录和审阅意见，无法作为枚举字段做统计或流转。

7. **配置前评估表残留了其他业务的示例内容。** 模板中的示例值指向另一条业务线，
   与本次北美 push 场景无关，说明模板被复制后未清理。

## 六、流程层面的观察

- **策略的预上线时间与观察时长集中在少数几个批次上**，而非逐条按需设定，
  说明是批量配置、统一观察；观察窗是否覆盖各自的典型周期，未被逐条单独验证。
- **阈值调整以「旧值划掉、括号内写新值」的方式就地修改**，台账里没有独立的变更记录字段，
  改动理由与改动时间不可追溯。
- **审批人与配置人分离、复核人固定为两人**，角色划分是清晰的；
  但 leader 审批人一栏普遍空白，最终签批人缺失。

**据此可提的改进项**：命中样本量为 0 时准确率应置空而非填 100%；
「是否达到命中样本参考门槛」应设为硬性卡点；黑产评估依据不接受占位符；
阈值变更应独立留痕（谁改、何时改、依据是什么）；「当前状态」应拆分为状态枚举 + 意见文本两栏。
